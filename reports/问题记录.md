# 实验问题记录

## P01：Decode Python/C ABI 参数数量不匹配（已修复）

- 发生阶段：首次执行 `python tests/test_correctness.py`，RMSNorm/GEMM 已通过，首次进入 Decode 时失败。
- 实际异常：`TypeError: this function takes at least 15 arguments (14 given)`。
- 原因：CUDA C 接口有 6 个指针、7 个整数、1 个 stream；ctypes 声明误写成 8 个整数。
- 修复：`lab.py` 中 `lab_decode.argtypes` 改为 `[P]*6 + [I]*7 + [P]`。
- 教训：FFI 签名必须逐项对照头文件。该错误发生在 CPU 绑定层，尚未启动 Decode kernel，不属于 GPU 数值误差。
- 回归结果：以最终 `raw/correctness.json` 和完整测试输出为准。

## P02：Nsight Compute 无性能计数器权限（环境限制，未解除）

- 实际错误：`ERR_NVGPUCTRPERM - The user does not have permission to access NVIDIA GPU Performance Counters on the target device 0`。
- 证据：`raw/ncu_gemm2.log`。
- 处理：未使用 sudo，未修改驱动配置；改用 ptxas 编译资源统计、CUDA Events 和 Nsight Systems。
- 已获得：寄存器/共享内存/编译器 spill 信息、实际 kernel 时间线及库后端名称。
- 未获得：实测 occupancy、DRAM 吞吐、bank conflict、warp stall 计数器。报告中的瓶颈分析明确区分代码推导与硬件测量。

## P03：RMSNorm 融合后反而更慢（已定位取舍，保留对照）

- T=1,H=4096：两 kernel 为 6.551 μs，融合 shared 版为 8.256 μs。
- 代码因素：为了支持 H≤8192，融合版每线程展开 32 个槽位，并保留数值；即使小 H 也存在条件判断与较大的生成代码。
- 编译证据：separate Norm 使用 32 个寄存器，fused shared 为 64 个；无编译器 spill。不能因此断言“已经测到 occupancy 降低”，实际计数器未获准使用。
- 已做改进：shuffle 版减到 54 个寄存器，half2 为 53 个；该形状 half2 降到 4.800 μs。
- 教训：减少启动和中间访存只是收益来源之一，仍需付出指令、寄存器和同步成本。进一步按 H 编译专用版本留作练习。

## P04：WMMA 在小 M 上更慢，且明显落后于库（已确认，未做全面调优）

- M=1,N=K=1024：naive 43.827 μs，shared tile 24.512 μs，WMMA 71.424 μs，torch.mm 4.461 μs。
- 原因分析：64×64 block tile 在 M=1 时大部分行无效；仍执行完整 tile 的 staging/MMA，只产生 16 个 block；GPU 有 82 个 SM。
- M=128,N=K=512 时，WMMA 仅 16 个 block，也落后于 tile16。
- 大矩阵受益：M=512,N=K=1024 时 WMMA 83.503 μs，naive 480.576 μs，但 torch.mm 仅 21.045 μs。
- 当前边界：没有寄存器级 CUDA core tile、异步拷贝、双缓冲和小 M 特化；本实现是正确且可分析的 WMMA 学习实现。

## P05：在线 Attention 少了中间数组，但更慢（已定位主要并行结构）

- B=1,Hq=32,Hkv=8,L=8192,D=128：三阶段 766.651 μs，在线单 block 1541.568 μs。
- 代码事实：在线版只有 32 个 block，每个 block 串行扫描所有 KV tile；每个 tile 有同步和串行 PV 累加。减少中间数组没有自动增加 GPU 并行度。
- 改进：Split16 将任务增加到 512 个 block，总耗时（含合并）127.680 μs。
- Nsight Systems 辅助证据：三阶段中的 PV 占主要时间；Split 的主 kernel 和合并 kernel 都实际执行。Profiler 时间单列，未混入主基准。
- 当前边界：相同长上下文下 SDPA Flash 为 58.617 μs，自写版本仍慢约 2.18 倍。

## P06：Split 数越多并非越好（已确认，自动分派留作后续）

- L=128 时 Split8 为 6.592 μs，Split16 为 7.280 μs；打乱顺序复测仍保持该趋势。
- 分片过细导致 tile 工作量下降、更多分片输出与合并读取，额外并行度收益不足以抵消成本。
- 当前提供显式 splits 参数，未把在五组形状上观察到的最优值包装成通用自动调优。

## P07：基准噪声与比较口径（已补充复测和边界）

- 主结果固定顺序运行，未锁定频率；部分记录的 P10～P90 组均值跨度约占中位数 11%。
- 处理：对 10 个关键配置做两轮打乱顺序复测，保存全部样本到 `raw/confirm.csv`，不挑选其中最快值替代主结果。
