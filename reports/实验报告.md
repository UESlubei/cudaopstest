## 1. 完成情况与核心结论

已完成三类算子的 CUDA C++ 实现、Python 接口、437 项正确性/契约检查、原生数值检查、四种 Compute Sanitizer 检查、80 组主性能记录、20 组打乱顺序复测及 Nsight Systems 时间线。这里的“三天”指学习安排，实验已在当前环境实际运行。

| 代表实验 | 基础版 → 优化版 | 主测加速比 | 需要保留的限制 |
|---|---|---:|---|
| RMSNorm，T=1024,H=4096 | separate 59.904 → half2 44.288 μs | 1.35× | 相对自写两 kernel 基线 |
| GEMM，M=512,N=K=1024 | naive 480.576 → WMMA 83.503 μs | 5.76× | WMMA 仍比 torch.mm 慢 3.97× |
| Decode，B=1,Hq=32,Hkv=8,L=8192,D=128 | online 1541.568 → Split16 127.680 μs | 12.07× | Split16 仍比 SDPA Flash 慢 2.18× |

本轮最关键的收获是：融合、Tensor Core 和分片都需要匹配工作量。减少中间数组或使用更强的计算单元，不会自动带来更低延迟。

## 2. 环境与实验口径

- GPU：RTX 3090，标称 24GB，Compute Capability 8.6，82 个 SM；驱动 570.86.15。
- CUDA Toolkit：12.8.93；GCC：9.4；Python：3.11.15；PyTorch：2.8.0+cu128。
- 编译：`nvcc -O3 -std=c++17 -arch=sm_86 -lineinfo`，未开启 `--use_fast_math`。生成共享库与独立 C++ 检查程序。
- FP16 输入/输出，RMSNorm/Attention 关键状态和 GEMM 累加使用 FP32。关闭 PyTorch matmul TF32 与 FP16 reduced precision reduction。
- 随机种子：20261014。全部输入驻留 GPU，输出/workspace 预分配，编译/分配/长度校验/主机传输不计入稳态时间。
- 每个实现先预热，再捕获包含 16 次完整算子的 CUDA Graph；再预热 10 次重放，测量 30 组。图内执行包含算子的全部 kernel，使用同一 stream 的 CUDA Events，报告每组平均耗时的中位数。
- P10/P90 是“组均值的分位数”，不是单次请求尾延迟。输入反复使用，因此是重复输入缓存条件；大工作集不保证所有数据都在 L2。
- 没有锁定时钟；主基准结束时设备处于 P2，约 52°C、265W。主结果存在频率/顺序偏差可能，另做打乱顺序复测。
- 这是 GPU 执行时间，不包含 Python ctypes 调用开销。未测完整模型吞吐、冷缓存或请求服务延迟。

## 4. 第一天：Residual Add + RMSNorm

数学语义：`U=fp16(float(X)+float(R))`，`Y=fp16(float(U)*rsqrt(mean(float(U)^2)+eps)*float(weight))`，输出 U 和 Y。首版 H≤8192。

四个自写版本分别是：Add/Norm 分开、融合+shared tree 归约、融合+warp shuffle 归约、融合+half2 读写。每行一个 256-thread block；融合版保留行值，避免归约后重新读取 U。half2 路径只在偶数 H 且所有指针对齐时启用。

全部结果如下，单位 μs：

| shape | separate | fused_shared | fused_shuffle | fused_half2 | torch_eager |
|---|---:|---:|---:|---:|---:|
| T1_H4096 | 6.551 | 8.256 | 8.056 | 4.800 | 15.744 |
| T128_H768 | 4.864 | 5.440 | 5.120 | 3.904 | 18.738 |
| T128_H4096 | 9.280 | 9.216 | 8.919 | 6.072 | 35.254 |
| T1024_H4096 | 59.904 | 59.648 | 55.872 | 44.288 | 242.420 |
| T1024_H8192 | 126.528 | 113.664 | 113.408 | 85.597 | 471.552 |

![RMSNorm 性能对比](/home/sdn/wjh/LLM-CUDA-KernelLab/reports/figures/rms.png)

观察与解释：

1. 在大输入上 half2 是本轮最快自写版本。T=1024,H=4096 相对 separate 为 1.35×。
2. scalar 融合不一定快。T=1,H=4096 时 fused_shared 明显慢于 separate；编译器报告显示保留行值使寄存器从 Norm 的 32 个增至 64 个，且代码为最大 H 展开，可能增加指令/资源成本。
3. shuffle 版用 54 个寄存器，half2 为 53 个，均无编译器 spill。寄存器变化是测得的编译属性；occupancy 和具体 stall 没有硬件计数器证据。
4. 忽略权重和缓存，separate 理想逻辑流量为 12TH 字节，融合为 8TH 字节；这不等于测得的 DRAM 传输量。T=1024,H=4096 的 half2 逻辑有效带宽约 757.6 GB/s。
5. `torch_eager` 是显式 FP32 归约的 PyTorch 组合表达式，包含多个中间算子；相对它的大倍数不能泛化为超过所有成熟融合 RMSNorm 内核。

## 5. 第二天：FP16 GEMM

语义：行主序 `C[M,N]=A[M,K]@B[K,N]`。naive 每线程一个输出；shared 版用 16×16 tile、FP32 shared staging；WMMA 版每 block 128 个线程，覆盖 64×64 输出，每个 warp 负责四个 16×16 fragment，K 每次推进 16。

WMMA 用对齐 shared memory staging，所有 M/N/K 尾部补零，并在最终写回屏蔽越界。该版本不是双缓冲流水线。PyTorch 基线使用预分配输出的 `torch.mm`，由当前 PyTorch/CUDA 库选择实现，没有额外做 cuBLASLt 算法调优。

| shape | naive | shared_tile16 | wmma_tile64 | torch_mm |
|---|---:|---:|---:|---:|
| M17_N65_K33 | 2.877 | 2.240 | 5.045 | 3.008 |
| M1_N1024_K1024 | 43.827 | 24.512 | 71.424 | 4.461 |
| M128_N512_K512 | 48.384 | 31.225 | 37.677 | 4.147 |
| M512_N1024_K1024 | 480.576 | 349.344 | 83.503 | 21.045 |
| M128_N4096_K4096 | 2101.247 | 1411.520 | 445.248 | 72.000 |

![GEMM 性能对比](/home/sdn/wjh/LLM-CUDA-KernelLab/reports/figures/gemm.png)

观察与解释：

1. M=512,N=K=1024 时 WMMA 对 naive 加速 5.76×，约 12.86 TFLOPS；torch.mm 仍快 3.97×。
2. 小 M 的 tile 浪费很明显。M=1,N=K=1024 只启动 16 个 WMMA block，且 tile 中 63 行无效；没有足够任务覆盖 82 个 SM。
3. M=128,N=K=512 也只启动 16 个 WMMA block；相比之下 tile16 可启动 256 个 block。此时 WMMA 低于 shared 版，与并行粒度和 staging 成本相符。
4. WMMA 编译资源：63 registers/thread，20480 bytes shared/block（4096 字节 A/B staging + 16384 字节输出 staging），无编译器 spill。
5. 与库的差距可能来自 tile/线程映射、串行装载与计算、同步、epilogue staging 等；没有计数器时不能将差距全部归因于某一种硬件瓶颈。

## 6. 第三天：Decode Attention

Q 为 `[B,Hq,D]`，KV 为 `[B,Hkv,L,D]`，`kv_head=query_head/(Hq/Hkv)`。每个 query 位于最后有效位置，可见 lengths 指定的全部历史。SDPA 对照使用 `is_causal=False`、无 dropout、`enable_gqa=True`，并强制 Flash 后端；本机所有主用例均可运行该后端。

三阶段版写 FP32 scores/probabilities；在线版每个 block 处理一个 query head，32 个 token 为一 tile，维护 FP32 最大值 m、指数和 l、未归一化输出 a。GQA 当前只实现正确映射，没有 query head 组内的 KV 共享。

在线更新与分片合并的共同原则是：改变最大值后，旧指数和与加权和必须一起重缩放。合并时 `m=max(m_s)`，`l=sum(exp(m_s-m)*l_s)`，`a=sum(exp(m_s-m)*a_s)`，最后 `O=a/l`；不能直接平均分片结果。空分片跳过，全空输出零。

| shape | three_stage | online | split2 | split4 | split8 | split16 | sdpa_flash |
|---|---:|---:|---:|---:|---:|---:|---:|
| B1_Q32_KV8_L128_D128 | 11.772 | 18.368 | 11.701 | 7.616 | 6.592 | 7.280 | 12.718 |
| B1_Q32_KV8_L2048_D128 | 195.008 | 387.072 | 196.928 | 101.952 | 56.384 | 33.984 | 23.742 |
| B1_Q32_KV8_L8192_D128 | 766.651 | 1541.568 | 776.414 | 396.832 | 213.877 | 127.680 | 58.617 |
| B4_Q32_KV8_L2048_D128 | 267.040 | 392.511 | 211.644 | 126.624 | 125.632 | 104.928 | 55.638 |
| B4_Q32_KV32_L2048_D64 | 270.907 | 499.200 | 260.570 | 145.920 | 149.599 | 123.836 | 168.000 |

![Decode 性能对比](/home/sdn/wjh/LLM-CUDA-KernelLab/reports/figures/decode.png)

观察与解释：

1. 在线单 block 版本在本轮五组形状中都落后于三阶段基线。它减少中间数组，但每个 head 仍需串行处理全部 tile，并执行多次同步，B=1 时总共只有 32 个 block。
2. 长上下文下 Split16 将任务从 32 个 block 增至 512 个，总时间包含主 kernel 和最终合并，相对在线版加速 12.07×；相对三阶段版为 6.00×。
3. L=128 时 Split8 比 Split16 快，两轮打乱顺序复测也保持该趋势；更细的分片增加状态和合并开销。
4. 长上下文下 SDPA Flash 仍快 2.18×；短序列或某个 MHA 形状自写实现更快仅属于该特定配置与比较口径，不能推广到全部模型。
5. B=1,Hq=32,L=8192 时，三阶段中间 workspace 为 2097152 字节（2 MiB）；Split16 为 266240 字节（260 KiB）。在线不分片算法无需中间数组，绑定只分配 4 字节占位。本统计不包括输入/输出或 SDPA 内部 workspace。
6. 单 query 分数数组是 O(B×Hq×L)，不是 prefill 的 O(L²)。

## 7. Profiler 与资源证据

Nsight Compute 实际失败：`ERR_NVGPUCTRPERM`。没有获取 DRAM 吞吐、bank conflict、实际 occupancy 或 warp stall。没有修改驱动权限以绕过限制。

替代证据分三类：

| 证据 | 已证明内容 | 不能由它直接推出的内容 |
|---|---|---|
| ptxas build.log | 寄存器、静态 shared、spill 编译结果 | 运行时 occupancy、缓存命中率 |
| CUDA Events / Graph | 固定条件下完整算子的 GPU 时间 | 主机调用延迟、服务吞吐 |
| Nsight Systems | 实际 kernel、顺序、单次时间线 | DRAM 饱和、bank conflict |

代表时间线中，在 B=1,Hq=32,Hkv=8,L=8192,D=128 上：三阶段 PV 约 721.283 μs，QK 110.560 μs，Softmax 8.576 μs；Split16 主 kernel 131.489 μs，合并 3.744 μs。它们来自独立 profiling 的单次运行，有测量扰动，不用于替换前面的主测中位数。

SDPA 对照实际出现 `pytorch_flash::flash_fwd_splitkv_kernel` 与 combine kernel，说明本次确实调用了库中的 Flash/Split-KV 实现，而非仅凭 API 名称推测后端。

RMSNorm 时间线确认 separate 是两个 kernel，融合版各一个；WMMA 分析应结合其代码与编译产物，不能仅由 kernel 名称断言计算单元利用率。

证据：[build.log](raw/build.log)、[kernel_resources.json](raw/kernel_resources.json)、[Nsight Systems 统计](raw/nsys_representative_stats.csv)、[Nsight Compute 失败日志](raw/ncu_gemm2.log)。原始 `.nsys-rep` 保存在 `reports/raw/`，可用 Nsight Systems GUI 打开。

## 8. 顺序与稳定性复测

针对关键结论做两轮打乱顺序测试，计时方法不变。主结果仍使用第一轮完整矩阵，没有挑选复测最小值替换。

| decode/B1_Q32_KV8_L128_D128 | 2_split8 | 7.488 | 6.647 |
| decode/B1_Q32_KV8_L8192_D128 | 1_split1 | 1525.374 | 1533.760 |

结论：关键收益和短序列 Split8 优于 Split16 的趋势保持；不同运行的细小差异应视为频率、缓存及测量扰动的一部分。本轮没有做统计显著性检验，不据微小差距宣称普适优势。
